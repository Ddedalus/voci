# pytest-testmon: mechanism report

Source read: `/home/hubert/voci/oss/pytest-testmon/testmon/{process_code,testmon_core,db,common,configure,pytest_testmon}.py` (total ~2600 lines) and `/home/hubert/voci/oss/pytest-testmon/tests/test_process_code.py` (the only test file present in this checkout — it pins down fingerprint/checksum semantics precisely; there is no test suite here for db.py/pytest_testmon.py behaviour, so those claims are read from source only).

## 1. Fingerprinting

**Block extraction** — `process_code.py:111-209` (`Module.blocks`, `Module.dump_and_block`). Source is `ast.parse`d once per file. `dump_and_block` walks the whole tree and produces a structural string (like `ast.dump(annotate_fields=False)`), but every time it meets a `Module`/`FunctionDef`/`AsyncFunctionDef` node's `body` field (`process_code.py:149-151`), it recurses into the list, then **replaces that list's representation with the opaque literal `"transformed_into_block"`** in the parent's string, and separately appends a `Block(start, end, code=<child string>, name=...)` to `self._blocks` (`process_code.py:170-186`). `ClassDef` bodies are *not* block boundaries — a method inside a class becomes its own block, but the class statement itself (and any plain top-level code) is folded into the enclosing block's text.

Net effect, confirmed by `tests/test_process_code.py::TestCodeToBlocks`:
- The **whole module is itself one block** spanning `first_stmt.lineno` to `len(lines)` (the `"<module>"` block).
- Each function/async function body is a separate nested block.
- A block's checksum only reflects **that scope's own statements minus nested function bodies** — editing inside `test_2`'s body does not change the module block or `test_1`'s block (`test_method_change_unexecuted1/2`).
- But a nested function's **signature** (name, args, decorators — everything in `FunctionDef` except `body`) is *not* hidden behind the placeholder, so it appears in the *enclosing* block's text. Renaming an uncalled function still invalidates any test that covered the enclosing scope (`test_method_name_unexecuted`, `process_code.py:150-163`).

**What is checksummed**: not source text, not line numbers, not code objects — a **structural AST dump** (`repr()` of AST leaf values via `ast.iter_fields`, `process_code.py:145-188`), CRC32'd per block (`to_signed(zlib.crc32(block.encode("UTF-8")))`, `process_code.py:17-39`). Consequences: comments and pure whitespace/formatting changes never move the checksum (they're not in the AST); line-number drift from unrelated edits elsewhere never moves it either, because line numbers are only used later to *map* coverage back to blocks, not to build the checksum.

**Non-Python files**: `ext != "py"` → the whole file is a single `Block(1, len(lines), whole_source)` (`process_code.py:207-208`) — one coarse fingerprint, any change to the file invalidates every test that touched it. Confirmed by `test_doctest_same/different` (`.txt` doctest files).

**Mapping coverage lines back to blocks** — `create_fingerprint` (`process_code.py:291-306`): blocks sorted by `start`, covered lines sorted; a single shared, monotonically-advancing `line_index` pointer skips lines strictly below the current block's `start`, then tests whether the next remaining line is `<= block.end`. This is an O(n+m) sweep that correctly matches a single covered line against *multiple overlapping blocks* (e.g. the whole-module block and a nested function block both containing line 2) because the pointer is never advanced past a line unless it's provably irrelevant to every later (higher-start) block too. A block only needs **one** covered line inside its range to be marked as executed.

**A test's dependency on a file** is stored as, per `(test, file)` pair: `filename`, `mtime`, `fsha` (content hash, see §7), and `method_checksums` = the fingerprint (list of block-checksums covered by that test) — built in `TestmonData.get_tests_fingerprints` (`testmon_core.py:296-319`) and persisted as one row per unique fingerprint in `file_fp`, linked via `test_execution_file_fp` (§6).

**"File changed but blocks unchanged" decision**: `match_fingerprint`/`check_fingerprint_db` — `set(old_fingerprint) - set(new_module.checksums)`; if every checksum the test used is still present among the file's *current* block checksums, nothing failed (`process_code.py:280-283`, `db.py:39-46`). A file whose fsha changed can still leave every test "stable" if none of the specific blocks a test touched changed.

## 2. Environment / bail-out

**Installed packages**: `common.py:76-87` (`get_system_packages`) enumerates `importlib.metadata.distributions()` → `"{name} {version}"` strings, sorted and joined into one big string; `drop_patch_version` (`common.py:90-95`) regexes `NAME M.N.P` down to `NAME M.N` so patch bumps don't count. This string, plus the interpreter's `major.minor.micro` (`testmon_core.py:214-215`), plus an `environment_name`, form a 3-column tuple.

**`environment_expression`/`--testmon-env`**: `--testmon-env` (CLI, `pytest_testmon.py:96-107`) or the `environment_expression` ini value evaluated via `eval_environment` — a literal `eval()` with `{os, sys, hashlib, md5}` in scope (`testmon_core.py:626-639`) — produces the `environment_name` string. Different environment names are **fully separate namespaces**: `environment` table is `UNIQUE(environment_name, system_packages, python_version)` (`db.py:343-351`), and every query that reads/writes `test_execution` filters by `environment_id` (`_test_execution_fk_column`). `file_fp` (the checksum table) has **no environment column** — block-checksum fingerprints are shared/deduplicated globally across all environments; only which-test-used-which-fingerprint is environment-scoped.

**Mismatch behaviour** — `DB.fetch_or_create_environment` (`db.py:647-711`): it looks up the **latest** row for that `environment_name` only (`ORDER BY id DESC` … `fetchone()`, ignoring package/version in the WHERE clause), then compares its stored `system_packages`/`python_version` against the current ones. If they differ: **insert a new environment row, then `DELETE FROM environment WHERE id = <old_id>`** (`db.py:697-709`). `test_execution.environment_id` has `ON DELETE CASCADE` (`db.py:362`), which cascades to `test_execution_file_fp` (`db.py:397`) — so a package/interpreter change **physically deletes every recorded test_execution row for that environment name**. `TestmonData.determine_stable` then finds `self.all_tests` (scoped to the new `exec_id`) empty, so every collected test is unstable → full rerun. `pytest_testmon.py:335-339` prints "The packages installed... have been changed. All tests have to be re-executed." No migration/merge, just a full wipe of that one environment's history (other differently-named environments in the same `.testmondata` file are untouched); on `finish_execution`, `vacuum_file_fp` (`db.py:111-116`, called from `db.py:103-109`) then deletes now-orphaned `file_fp` rows.

## 3. Non-Python files and third-party code

Tracking is delegated entirely to what `coverage.py` is configured to instrument: `TestmonCollector.setup_coverage` (`testmon_core.py:487-525`) sets `include=[rootdir/*]` (extended with pytest-cov's `cov.config.source`/`run_include` if pytest-cov is also active) and `omit` = every `sysconfig.get_paths()` value whose key ends in `"lib"` (stdlib + site-packages, `testmon_core.py:490-494`). So:
- Files under `rootdir` (any extension coverage can report a line for) are trackable.
- `site-packages`/stdlib are explicitly omitted — third-party code is invisible to per-file fingerprinting. This is *why* the coarse `system_packages` string (§2) exists: it's the only signal for dependency changes at all.
- Pure data files (JSON/YAML/templates/etc.) are never traced regardless of location, because `coverage.py`'s tracer only ever fires for Python execution — `open()`ing a file produces no coverage event for that file.
- No declared "which files are tracked" config beyond `include`/`omit`; there's no source-root-vs-editable-install distinction at all (this is the "coverage.py already knows the real executing file" idea the plan attributes to Option B).

## 4. Selection algorithm

Core is a single SQL query per session: `TestmonData.determine_stable` (`testmon_core.py:346-372`).
1. Compute current `fsha` for every filename previously seen (`files_of_interest` = **all** filenames ever recorded in `file_fp`, across all environments — `db.py:612-622`, `initiate_execution` returns `self.all_filenames()`).
2. `db.fetch_unknown_files` (`db.py:462-491`): files whose current fsha differs from (or has no row in) the environment's own recorded fshas → `new_changed_file_data`.
3. `collect_mhashes` (`testmon_core.py:149-154`) recomputes block checksums only for those changed files.
4. `db.determine_tests` (`db.py:496-559`): joins `test_execution`/`test_execution_file_fp`/`file_fp` against the changed-file mhashes; any test whose stored fingerprint for a changed file has checksums not present in the new block set is a **method_miss** → `affected_tests`.
5. `unstable_test_names = affected_tests`; `stable_test_names = all_tests - unstable_test_names`.

**Failing tests always rerun**: `get_failing` (`pytest_testmon.py:488-494`) reads `failed` bit from `all_test_executions`; `TestmonSelect.__init__` (`pytest_testmon.py:520-529`) explicitly removes any test/file that's in `failing_files`/`failing_test_names` from the deselect list, independent of fingerprint match. `determine_tests` also independently returns a `failing` list (`db.py:544-559`) unioned via `self.failing_tests`.

**New/unknown tests** — `TestmonCollect.pytest_collection_modifyitems` → `sync_db_fs_tests` (`pytest_testmon.py:377-386`, `testmon_core.py:321-344`): every newly-collected test not yet in `db.all_tests` gets a **placeholder fingerprint** — `method_checksums = methods_to_checksums(["0match"])`, a fixed sentinel string, `mtime=None`, `fsha=None` (`testmon_core.py:329-336`). A `NULL` `fsha`/sentinel checksum can never match a real file's checksums, so `fetch_unknown_files`'s `f.fsha IS NULL OR chff.fsha IS NULL` clause (`db.py:485-486`) always flags that filename as changed, guaranteeing the brand-new test is selected the first time — it only becomes "known"/matchable once it actually executes and a real fingerprint overwrites the sentinel (`insert_test_file_fps` does delete-then-insert per test name, `db.py:257-267`).

**Deleted/renamed tests**: same `sync_db_fs_tests` — `to_delete = db.all_tests - collected` (`testmon_core.py:342`) triggers `db.delete_test_executions` (`db.py:561-578`), purging their rows. This sync is skipped if `session.testsfailed` is set at collection time (`pytest_testmon.py:381-384`), i.e. collection errors block pruning that run.

**`-k`/`-m`/`--lf`/explicit nodeids**: `configure.py:65-85` (`_get_noselect_reasons`) forces `select=False` (still reorders by duration and *collects* new data, just doesn't deselect) whenever `-k`, `-m`, `--lf`, or an explicit `file.py::test` argument is present — unless `--testmon-forceselect` is passed, which short-circuits straight to `[]` (`configure.py:66-67`), letting selection and pytest's own selectors combine.

**Tests never run / interrupted mid-run**: if a test raises through `pytest_runtest_protocol`, `TestmonCollect` calls `self.testmon.discard_current()` (`pytest_testmon.py:388-396`), which makes `get_batch_coverage_data`/`get_nodes_files_lines` drop that test from the batch (`.pop(dont_include, None)`, `testmon_core.py:599-601`) — no (possibly-truncated) fingerprint is ever written for it, so its old fingerprint (or "0match" sentinel if new) stands and it will be selected again next run.

## 5. Data collection

One `coverage.Coverage` object per process, **not** per test (`testmon_core.py:520`, built in `setup_coverage`), started once (`start_cov`, `testmon_core.py:468-471`) and kept running across a *batch* of up to `TEST_BATCH_SIZE = 250` tests (`testmon_core.py:43`). Per-test attribution uses coverage.py's **dynamic contexts**: `self.cov.switch_context(test_name)` (`testmon_core.py:536`) is called once per test inside `start_testmon`, invoked from the `pytest_runtest_protocol` hookwrapper (`pytest_testmon.py:389-392`) — so the context spans **setup + call + teardown** of that one item. At flush time, `get_nodes_files_lines` reads `cov_data.contexts_by_lineno(file)` (`testmon_core.py:591`) and builds `{test_name: {filename: {linenos}}}`.

Batching/flush triggers (`get_batch_coverage_data`, `testmon_core.py:542-581`): batch full (250 tests), `next_test_name is None` (last item of the session), or an interruption — `self.cov.stop()`, harvest, `self.cov.erase(); self.cov.start()` to reset for the next batch (keeps the sqlite coverage-data structure bounded).

**Fixture scope gap — not solved by testmon**: because a `scope="session"`/`"module"` fixture body executes exactly once, coverage lines for it are recorded only under whichever `test_name` was the active context at that moment; later tests that reuse the already-initialized fixture get **no coverage record for it at all**, so no dependency is stored for them. No special-casing was found anywhere for this (no fixture-graph awareness in this codebase) — it's an accepted structural limitation, matching what the project's own plan calls out as the shared-scope hole for Option B to close statically.

**Import-time / module-level code**: attributed entirely to whichever test happens to be the *first* one to import the module in that batch/process (its context is active at that instant) — same "only recorded for whoever ran it once" pattern, and the module fully invalidates for anyone whose fingerprint includes that whole-module block (see §1's module-block mapping) since import always executes at least line 1.

A guaranteed floor exists: every test that produced *any* coverage this batch gets its own home file force-added even with zero interior hits — `nodes_files_lines[test_name].setdefault(home_file(test_name), {1})` (`testmon_core.py:602-604`) — so a test always depends at least on its own module.

## 6. Storage

Single SQLite file (`.testmondata` by default, `testmon_core.py:46,51-52`), opened with `PRAGMA journal_mode = WAL; synchronous = OFF` (`db.py:31-32`). Tables (`db.py:340-409`):
- `metadata(dataid PK, data)` — free-form counters/attributes (`write_attribute`/`fetch_attribute`, keyed `"{exec_id}:{attribute}"`; global stats use `exec_id=None`).
- `environment(id PK, environment_name, system_packages, python_version, UNIQUE(all three))`.
- `test_execution(id PK, environment_id FK CASCADE, test_name, duration, failed, forced)`, indexed on `(environment_id, test_name)`.
- `file_fp(id PK, filename, method_checksums BLOB, mtime, fsha, UNIQUE(filename, fsha, method_checksums))` — the **deduplicated fingerprint table**: identical `(filename, fsha, checksums)` triples across many tests collapse to one row via `fetch_or_create_file_fp` (`db.py:195-224`, an `lru_cache`d insert-or-select), so N tests sharing the same view of a file cost one row, not N.
- `test_execution_file_fp(test_execution_id, fingerprint_id)` — the many-to-many junction, is the actual per-test dependency set.
- `suite_execution_file_fsha` — a coarser duplicate table described in its own DDL comment as "for faster queries"; its populate hook `insert_into_suite_files_fshas` is a no-op `pass` in the OSS `DB` class (`db.py:299-300`) — vestigial/unused here (likely wired up only in the proprietary tmnet server DB subclass).
- Two `TEMPORARY` tables (`changed_files_fshas`, `changed_files_mhashes`, `db.py:369-376`) used as scratch join tables for the per-run comparisons in §4, recreated each connection.

**Checksums stored as blobs**: `array('I', checksums).tobytes()` (`checksums_to_blob`/`blob_to_checksums`, `process_code.py:42-51`), i.e. a packed array of 32-bit ints, not JSON.

**Schema versioning**: `PRAGMA user_version` holds `DATA_VERSION = 14` (`db.py:13,49-59,423`). `check_data_version` compares it to the code's constant; **any mismatch closes the connection, deletes the file, and reinitializes empty** (`db.py:55-59`) — no migration path at all, a version bump is a full wipe.

**Concurrency / xdist**: workers open the DB **read-only** (`connect(..., readonly=True)` → SQLite URI `?mode=ro`, `db.py:24-27`; `TestmonData.for_worker(..., readonly=True)`, `testmon_core.py:248-262`). Workers never write: `TestmonCollect.pytest_runtest_logreport` returns immediately `if self._running_as == "worker"` (`pytest_testmon.py:409-411`). Instead each worker computes its own `nodes_files_lines` locally and stashes it on the pytest `TestReport` object (`report.nodes_files_lines = ...; result.force_result(report)`, `pytest_testmon.py:397-406`), which xdist pickles back to the controller; the **controller's** plugin instance is the only one whose `pytest_runtest_logreport` actually calls `save_test_execution_file_fps` (`pytest_testmon.py:412-421`). So there is exactly one writer (the controller process) for the whole session — concurrency safety comes from architecture, not from locking. Controller also precomputes `exec_id`/`system_packages_change`/`files_of_interest` once and pushes them to workers via `TestmonXdistSync.pytest_configure_node`/`workerinput` (`pytest_testmon.py:447-471`) so workers skip redundant environment/package detection.

**Whole-DB invalidation triggers**: (a) `DATA_VERSION` mismatch (file deleted), (b) environment/package/python-version change (cascade-deletes that one environment's rows, §2) — nothing else forces a full-DB wipe; a normal changed-source-file run only touches the affected rows.

## 7. Stale-data handling

Staleness is decided **purely by content hash (`fsha`), never by `mtime`**, despite `mtime` existing as a column on `file_fp` and being tracked on `Module` (`testmon_core.py:84-102`, `process_code.py:125,213-215`). The functions that would compare mtimes — `check_mtime`, `check_fsha` (`testmon_core.py:105-121`), and the batch helpers `split_filter` (`testmon_core.py:133-141`), `get_new_mtimes` (`testmon_core.py:411-422`), `db.update_mtimes` (`db.py:97-101`), plus `db.fetch_changed_file_data`/`ChangedFileData` (`db.py:15-17,425-460`) and `process_code.GAP_MARKS`/`INVERTED_GAP_MARKS_CHECKSUMS` (`process_code.py:54-57`) — are **never called from the live selection path** (`determine_stable`→`fetch_unknown_files`/`determine_tests`), confirmed by grepping the whole package for callers outside their own definitions. They read as vestiges of an earlier two-tier "cheap mtime check, only hash on mismatch" design that was superseded by the current pure-fsha SQL join and left in place unused.

**Content hashing is git-blob-compatible**: `bytes_to_string_and_fsha` (`process_code.py:87-99`) computes `sha1("blob {len}\0" + bytes)` — exactly `git hash-object`'s algorithm. `get_source_sha` (`process_code.py:266-272`) first tries `get_files_shas(rootdir)` (`process_code.py:235-263`, backed by `git ls-files --stage -m`), which gives the **staged/committed blob sha for unmodified tracked files without reading them off disk at all**; any file `git status` reports as modified is explicitly excluded from that map (`modified_files` handling, `process_code.py:248-257`) and falls back to reading+hashing straight off disk. Net effect: a branch switch or rebase that rewrites mtimes but leaves content (and its git blob) identical produces the **same fsha**, so nothing gets marked changed — mtime churn is a non-event by construction, without ever consulting mtime.

**File deletion**: a deleted source file simply stops appearing in the filesystem scan; `SourceTree.get_file` catches `FileNotFoundError`/`get_source_sha` returns `(None, None)` (`testmon_core.py:84-102`, `process_code.py:222-232`) → `files_fshas` omits it, so `fetch_unknown_files`'s join treats any test whose fingerprint referenced it as unmatched (its stored fsha now has no counterpart) → those tests become unstable/selected, and will presumably fail at collection/import if they truly depended on the missing file. **Test file deletion** is handled at the test-node granularity by the `sync_db_fs_tests` delete-path in §4 (rows removed once collection no longer reports that nodeid).

## 8. Clever/surprising bits and soundness observations

- **No `conftest.py`/`__init__.py`/`pyproject.toml` special-casing exists anywhere in this code.** They're plain files under `rootdir`: `conftest.py` gets fingerprinted exactly like any other module via whatever coverage records for it (so a `conftest.py`-defined session fixture inherits the exact same "only the first test that ran it gets the dependency" gap as any other shared setup, §5); the plugin's own config files (`pyproject.toml`, `setup.cfg`) aren't tracked as dependencies at all — a `[tool.pytest.ini_options]`/`environment_expression` edit is invisible to fingerprinting (matches the plan's "`[tool.voci]` itself" risk item).
- **The "0match" sentinel fingerprint** (`testmon_core.py:329-336`) is a neat, minimal trick for "force-select on first sight": rather than a null/absent-row special case threaded through every query, a genuinely-unmatchable placeholder checksum makes the *existing* comparison machinery naturally always flag the test as changed.
- **Environment change is implemented as row deletion + FK cascade**, not a boolean flag consulted downstream — reusing `ON DELETE CASCADE` to get "wipe this environment's history" for free from two SQL statements (`db.py:697-709`).
- **xdist concurrency is solved architecturally** (workers read-only, single controller writer, results piggy-backed on pytest's own report-serialization channel) rather than via database-level locking — directly reusable even outside sqlite.
- **`file_fp` dedup is global across environments**, but `files_of_interest`/`all_filenames()` (used to decide which files to even check this run) is also **global across environments** (`db.py:612-622`) — an environment switch still re-hashes files that only ever mattered to some *other* named environment, a minor wasted-work rather than correctness issue.
- **Coverage-object stacking for "dogfooding"** (`TestmonCollector.coverage_stack`, `testmon_core.py:441,468-525,542-624`): when pytest-cov is also active, testmon temporarily stops the outer `Coverage`, runs its own instrumented one, and on batch flush replays a filtered subset of its own line data back up into the outer coverage object (via `should_include`, `testmon_core.py:144-146`) so overall coverage reporting stays correct despite testmon owning the trace function for its own bookkeeping.
- **Confirmed dead code**: `check_mtime`, `check_fsha`, `split_filter`, `db.fetch_changed_file_data`/`ChangedFileData`, `db.update_mtimes`, `testmon_core.get_new_mtimes`, and `process_code.GAP_MARKS`/`INVERTED_GAP_MARKS_CHECKSUMS` have no callers anywhere in the package (grep-verified) — remnants of an abandoned mtime-first design.
- **Soundness holes worth flagging for our design**: (1) shared-scope fixtures attributed to a single arbitrary test, unaddressed (§5) — exactly the hole the voci plan's "static fixture union" step is meant to close, confirming that idea has no analogue to borrow from testmon, it must be built fresh; (2) `TestmonXdistSync.pytest_xdist_node_collection_finished` (`pytest_testmon.py:476-481`) calls `sync_db_fs_tests(retain=set(ids))` using only the *last-reporting* worker's collected id list, not a union across workers — correct only because xdist's default scheduler makes every worker collect the identical full suite; a custom/partial-collection scheduler would silently under-populate `retain` and could prune live tests.

## Directly reusable ideas for a sys.monitoring-based design

- **Structural checksum per function, computed from AST, not source text or line numbers** (`process_code.py:134-188`): hashing `ast.dump`-equivalent text (or something similar keyed off `ast.unparse`/normalized node fields) per function, rather than raw text, makes fingerprints immune to comment/whitespace-only edits and to line-shifts from unrelated edits — worth adopting in place of a plain source-text hash per `qualname`, since it buys that insensitivity for free (assertion rewriting, mentioned as a risk in the plan, is the one place where staying with source-text-post-rewrite hashing might still be simpler, but the AST-normalization trick is available if source-text churn turns out to be a problem).
- **Sentinel fingerprint for "test never executed"** (`testmon_core.py:329-336`): give brand-new/unrun tests a fixed unmatchable marker in storage so the existing "does the stored set survive?" comparison naturally forces them to run, instead of a separate code path for "test has no history."
- **Single-writer architecture under concurrency**: only one process/thread ever appends to the store; other workers compute locally and hand results back through an existing result-carrying channel (report objects / `isolated.result_to_json`) rather than writing the database directly — this maps cleanly onto voci's `@voci.isolated` subprocess boundary already called out in the plan.
- **Environment identity as one small hashable tuple gating a whole-namespace wipe**, using a DB-native cascade-delete rather than an application-level "is everything stale" flag — cheap to implement and cheap to reason about.
- **Deduplicating the fingerprint/dependency-set storage via a `(filename/qualname-set, hash) UNIQUE` insert-or-fetch table** (`fetch_or_create_file_fp`, `db.py:195-224`) rather than storing a fingerprint blob per test row — directly addresses the plan's "per-test sets are much larger than existing caches" sizing concern.
- **Schema-version-as-`PRAGMA user_version`, mismatch ⇒ delete-and-recreate**: simplest possible migration story, matches voci's existing "atomic replace, no partial migration" discipline in `_cache.py`.
- **Explicit, user-facing deactivation reasons** (`configure.py:24-95`) — a small pure function mapping CLI/ini state to a one-line "selection disabled because -k was used" message is worth copying verbatim as a pattern for voci's own bail-out reporting.

## Where their approach depends on coverage.py line data and would not transfer

- **The entire fingerprint-creation step operates on covered *line numbers***, not executed functions: `create_fingerprint`'s block-matching sweep (`process_code.py:291-306`) exists specifically to translate `coverage.py`'s per-line `contexts_by_lineno` data (`testmon_core.py:591-598`) into "which of my statically-computed blocks did this line fall inside." A `PY_START`-based tracer already knows the executed function directly (`(filename, qualname)` at the frame) — there is no line-to-block mapping problem to solve, and the whole `Block(start, end, ...)` / sweep apparatus in `process_code.py` has no counterpart to build.
- **The "does this block contain at least one covered line" test** (and the resulting subtlety that a module-level block gets marked "touched" merely because an unrelated import line executed) is a coverage-line artifact. Under PY_START, module-level code is either executed (the module object's top-level frame runs) or not — no partial/line-granularity ambiguity, but also no way to get *finer* than whole-module-body granularity for module-level code (same conclusion, reached by a different path).
- **Batching coverage data for memory reasons** (`TEST_BATCH_SIZE = 250`, stop/erase/restart cycle, `testmon_core.py:542-581`) is specific to `coverage.py`'s underlying SQLite-backed `CoverageData` growing unboundedly across a session; a `ContextVar`-attributed `PY_START` callback writing directly into per-test in-memory sets has a different (and likely much cheaper) memory profile and would use its own batching policy, not this one.
- **`cov.switch_context(test_name)`** (`testmon_core.py:536`) is `coverage.py`'s specific dynamic-context API; the plan's `ContextVar`-read-in-callback approach is a different (and, per the plan's own prototype results, concurrency-safe at parallelism > 1 in a way `coverage.py` contexts were never designed for) mechanism — nothing about testmon's context-switch call transfers, only the *goal* (per-test attribution without stop/restart) does.
- **The `should_include`/coverage-stack replaying logic for pytest-cov coexistence** (`testmon_core.py:144-146, 565-579`) is entirely about two `Coverage` objects sharing one C-level trace function slot; `sys.monitoring` (Python ≥3.12) is a multi-tool-ID API (the plan already notes IDs 0/1/2/5 are reserved for debugger/coverage/profiler/optimizer) precisely so this kind of manual stacking/replay is unnecessary — a testmon-equivalent coexistence problem with `pytest-cov` would be solved by picking an unused tool ID, not by porting this code.
- **`method_checksums`/block-checksum blobs keyed by covered-line-derived block identity** (`process_code.py:34-39`, `db.py` `file_fp.method_checksums`) assume the granularity units are discovered by intersecting a static block map with dynamic line coverage; under PY_START the granularity unit (the function) *is* the thing directly observed at runtime, so the fingerprint can be `{qualname: source_hash}` with no intersection step at all — simpler, but means none of `process_code.py`'s block/line-sweep code is reusable, only the general "hash the AST-normalized body per unit, dedup identical dependency-sets in a fingerprint table" ideas above.
